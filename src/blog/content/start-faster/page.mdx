During my time at [Gardener's](https://www.gardeners.com), one of my primary
goals was to improve the performance of the site. When I joined, every metric in
our lighthouse report was on fire, but in the year and a half I was there, the
team and I made great progress. We sped up page load, reduced layout shift, and
optimized SEO. Unfortunately, all of these changes got thrown away when the
company was acquired[^1].

Since the work we did is gone, I wanted to create a project that encapsulated
all of the things we learned along the way. This is what lead me to build
[Start Faster](https://www.start-faster.com). The purpose of this shop isn't to
make money, its to demonstrate how fast an e-commerce platform can be.

## What is Start Faster?

Start faster is an evolving suite of tools for building an online shop. It
includes a custom storefront for your Shopify catalog, a CMS for managing site
content, and an admin portal for managing user permissions.

## What is the stack?

- [TanStack Start](https://www.tanstack.com/start/latest) + React
- [Convex](https://www.convex.dev) for the CMS and admin portal
- [Shopify](https://www.shopify.com)
- [Vercel](https://www.vercel.com)

## Why use your own site in front of Shopify? Why not just use Shopify's site?

Shopify is an excellent product. They have built an incredible set of tools that
allows you to get selling in no time. Order management and payment processing
are difficult problems to solve, and I don't think it makes sense to re-invent
the wheel. That said, I do think there is still merit to building your own
custom storefront for web/mobile. Having greater control over the user
experience and performance of your storefront allows you to deliver your
customers the exact experience you want them to have. And while Shopify's
provided storefront's and custimization tools are good, they will never match
the freedom of owning the code yourself. The Start Faster storefront is a
TanStack Start + React web app making calls to Shopify's
[Storefront API](https://shopify.dev/docs/api/storefront/latest).

## What makes the project so great?

There isn't one thing that makes it great, its a homogenous mix of good stack

Lets dive deep into a few of the things that shine the brightest:

### Storing state in the URL

If you want to:

- Persist state between page reloads
- Persist state when sharing links between users
- Persist state for bookmarked URLs
- Apply filters or sorting options on navigation

Then the URL might be the perfect place for you to store your state. This is
especially the case for e-commerce platforms. When a customer bookmarks a shirt
in a specific size and color, that bookmark should open the page to that exact
product variant. If they're on a search page and refresh the page, their filters
should persist.

The issue is that most meta-frameworks don't provide a way to access and set URL
params in a type-safe manner. In Next.js, accesses are always typed
`string | undefined`, and you can set them to be whatever string you'd like.
When it comes to validating their types and values, the ball is in your court.

One of the reasons Tanner Linsley built TanStack Router (the core of TanStack
Start) is becuase he wanted a way to treat the URL as a predictable
[state management solution](https://tanstack.com/blog/search-params-are-state)
with good DX. In Start, you define your URL params at the Route level with the
validator of your choosing[^2]. When you access them, they will be typed as the
return type of their validator. When you set them, you will get a type error if
the value you provide does not match the validator return type. If the values in
the user's URL don't pass validation, they will hit the error boundary.

[^2]:
    As long as it meets the [Standard Schema](https://standardschema.dev/schema)
    spec.

```tsx
import { createFileRoute } from "@tanstack/react-router";
import { z } from "zod";

export const Route = createFileRoute("/dashboard")({
  component: DashboardRoute,
  validateSearch: z.object({
    q: z.string(),
    tab: z.enum(["General", "Sales", "Marketing"]).default("General"),
  }),
});

function DashboardRoute() {
  // typed as string
  const queryParam = Route.useSearch({ select: (search) => search.q });

  // typed as "General" | "Sales" | "Marketing"
  const currentTab = Route.useSearch({ select: (search) => search.tab });
}
```

When you access one of these parameter values, you know exactly what the type of
the data will look like, no surprises. If the value of the param changes, the
component will re-render in true React fashion.

> [!tip] You should always use the `select` option when using the `useSearch`
> hook. This way, the state variable will only change and cause a re-render when
> the selector expressions changes, not when any single URL param changes.

If you check out
[this page](https://www.start-faster.com/search?q=alien&sortBy=price&sortDirection=asc&filters=%5B%7B"price"%3A%7B"max"%3A50%7D%7D%5D)
on Start Faster, you can see these principles in action. When you open the page,
the search bar contains the search term I entered, and the filters and sorting
are preserved. Go ahead and change them, refresh, and see for yourself!

### Aggressive caching and preloading

When you navigate between pages on Start Faster, you'll notice that most of the
time you instantly land at the destination page. This is due to:

1. Route caching
2. The
   ["Quick Link"](https://github.com/bentsignal/start-faster/blob/main/packages/features/src/quick-link/quick-link.tsx)
   component

Route caching comes out of the box with TanStack Start. You can configure till
your hearts content, but the defaults are great.

The quick link component does not come with Start. It a custom component[^3]
that replaces the TanStack Start `<Link>` component. It makes it so that
navigation happens on mouse down instead of mouse up, which provides faster INP.
It also sets a dynamic default for preloading behavior. On screens with a mouse
cursor, links are preloaded when they're hovered. On touch screens, they're
preloaded when they enter the viewport. This ensures that navigations happen as
quick as possible, no matter what platform you're browsing on.

[^3]:
    This component is heavily inspired by
    [Next Faster](https://github.com/ethanniser/NextFaster), an e-commerce
    template created by [Ethan Niser](https://x.com/ethanniser) and
    [Rhys Sullivan](https://x.com/RhysSullivan). Their project was a huge
    inspiration for the name "Start Faster", as well as the creation of the
    project itself.

### Images

E-commerce sites demand large high quality images, so its important to load them
with speed and grace.

To handle speed, I just used Vercel's
[Image Optimization](https://vercel.com/docs/image-optimization). Shopify
already puts a CDN in front of their images, but I found that the load times
felt significantly faster when putting Vercel between the images from Shopify
and the user. It took a bit of extra configuration since I'm not using Next.js,
but it wasn't too bad.

Getting images to load gracefully was more difficult. Most browsers have decent
image loading behavior, but some (firefox) do not. The solution I arrived at was
to avoid the default browser behavior at all costs. The philosopy is as follows:

1. If the image has not yet been loaded, show nothing at first. Then fade the
   image in after it loads
2. If the image has previously been loaded in this session, show it immediately.

I found this to be the best possible configuration. Navigating back and forth
between pages avoids replaying the loading animation, while first time page
loads have no flicker.

### Optimistic Updates

Whenever possible, I try to make sure that something happens immediately when
the user performs an action. There should always be some sort of indication that
the action they attempted to take was receieved. Ideally, you can even show them
the anticipated response immediately, even if the server hasn't confirmed it
yet, i.e. an _Optimistic_ update.

The place I think benefitted most from Optimistic Updates is the cart. You click
"Add to Cart" on an item, it immediately appears in your cart list, even though
the server hasn't sent back the new cart data yet. You can spam the buttons to
increase or decrease quantity as fast as you'd like, the final amount shown will
always be right.

The key to doing this was to not show the cart data last sent from the server,
but to show what it would look like if all of the outgoing mutations were
applied to it. Since the mutation is no longer pending as soon as the new
response data comes back, it stays perfectly in sync. The user has no idea that
they don't actually have their current cart data, they just see what they expect
to see.

The are some places where Optimistic updates don't make sense or are impossible.
You can't really use them when applying filters to the search page for example.
But when they can be used, I believe they usually should.

#### End to end reactivity

One of my favorite features in the CMS is being able to quickly change between
the editor, and the live preview as you work. When you write a new paragraph in
the WYSIWYG editor and switch to the preview, it will show up instantly.

This is all thanks to [Convex](https://www.convex.dev).

The basis of Convex is queries & mutations, which are similar to pub/sub. When a
mutation is performed, the affect subscriber query in the client immediately
gets the new value. When you type into the editor in the CMS, the content is
saved to the db. The preview page then gets the new value and shows it
immediately.

This might not sound new, but what makes convex special is:

1. How few lines of code are required to do this
2. The speed at which everything happens
3. The fact that they handle query caching for you

That last one is enormous. Requesting the value from a query that hasn't changed
since its last call doesn't run the query again, you just get the cached value.
This reduces cost for you (since convex doesn't charge for cache hits), and
reduces latency for your users. No more headaches over cache invalidation, lets
them handle it for you.

I could spend all day talking about why I love Convex, but we'll save that for
another day.
